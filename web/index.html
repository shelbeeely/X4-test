Xteink X4 Debug Firmware

Display bring-up / debug build for the Xteink X4 (ESP32-C3)

Flashes the latest CI build and lets you watch its serial debug output — both straight from Chrome over WebSerial, no drivers or command line needed.

Requires Chrome or Edge on a computer (a Chromebook works fine), with the X4 connected over USB. Web Serial isn't available in mobile browsers.

1. Flash

Your browser doesn't support Web Serial — open this page in Chrome or Edge instead. This page needs to be served over HTTPS to flash (it is here — try reloading).

Auto-flash: grant access once and leave this tab open — it checks for a newer build about once a minute and reflashes on its own the moment one lands, no further clicks. It reuses whatever WebSerial permission you've already granted (here or in the monitor below); if none exists yet, enabling it prompts you for the port once.

Auto-flash is off.

This tab has to stay open (and the computer awake) to keep checking and flashing — there's no background service. If the board's USB identity changes between normal operation and the bootloader it drops into mid-flash, the browser may ask you to re-pick the port on the next cycle instead of reconnecting silently; that's a Chrome/WebSerial behavior this page can't control, not a bug here.

2. Watch the debug output

Opens a live 115200-baud console right in this page. Works whether you just flashed above or the X4 is already running this firmware from before — it's a separate WebSerial connection from the flasher, so close the install dialog first if it's still open.

    After connecting, reset the board (or replug USB) to see the full boot
    log from the start: [XTDET] lines from the panel-controller
    probe (X4-family units ship SSD1677, UC8179, or UC8279 depending on
    production batch — sending the wrong one's commands is the classic
    "screen stuck on its last image" cause, so this runs and promotes the
    driver automatically before anything touches the panel), the
    BoardConfig pin dump (display and button pins),
    display geometry, and initial refresh timing. The board then boots into
    an on-device test menu — UP/DOWN to select, CONFIRM to run, BACK to
    exit a running test — covering the original pattern, a
    checkerboard ghosting check, a FULL/HALF/FAST refresh-mode comparison, a
    partial-window update test, a live button/ADC readout, a review of the
    controller-probe result, and the original continuous flash-stress loop;
    each run logs an === TEST: ... === block. A
    [BTN] line is logged on every button press/release (or
    roughly every 2s while idle) regardless of which screen is active,
    carrying the raw ADC reading for both button groups so a drifted or
    flaky divider is visible even without a full press.
  


  
3. Show the AI a photo of the panel (optional)

  

    Uses this device's camera to capture a still of the physical e-paper
    panel, so the AI can check whether it visually matches what the active
    test screen is supposed to look like — not just whether the
    firmware logged success. Point the camera at the panel before
    capturing.
  

  

    
    
    
  

  
  
  
  
Camera access requires your permission and isn't stored anywhere — only the captured still is (in this page's memory) until you clear it or reload.


  
4. Ask an AI about the log (and photo)

  

    Paste an OpenRouter API key to
    send whatever's currently in the console above — plus the captured
    photo, if you took one — to an LLM for a second opinion. Useful for
    spotting hardware issues (a stuck BUSY pin, odd refresh timing, button
    ADC readings sitting on a classification boundary, missing events, or a
    panel that visually doesn't match what a test screen should show) that
    are easy to miss skimming a long log by eye.
  

  

    Your key (and the captured photo, when you send one) go only from this
    browser straight to OpenRouter's API — this page is static with no
    server of its own to see either.
